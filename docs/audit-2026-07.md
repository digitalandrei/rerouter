# Rerouter — Security & Safety Audit (2026-07)

**Date:** 2026-07-02 · **Commit audited:** `b46952d` (main, after merging `feat/sflow-support`) ·
**Baseline:** [audit-2026-06.md](audit-2026-06.md) (`12b254a`) · **Auditor:** Claude (Fable 5)

## 1. Scope & method

Full re-audit of the doctrine (`docs/doctrine.md`, `CLAUDE.md`) and the whole tree — Rust controller,
React SPA, and `deploy/` — with the June audit as the baseline to diff against.

The delta since the June baseline is only **3 commits**: `b46952d` (sFlow v5 decoder — new, never
audited), `8e74ed5` (exporter-map LRU cap — closes June P1-3), and `b86269a` (crash recovery made
mandatory + fail-closed — closes June P1-1/P1-2). But two whole surfaces were **out of scope in June
and audited here for the first time**: (a) the **flow collector as a live path** — since `b46952d` +
the `detection/engine.rs` wiring, NetFlow/sFlow are no longer inert stubs but an
*untrusted-UDP → detection → automatic-reroute* chain; and (b) the **React SPA** and **`deploy/`**
configs. That new coverage is why this audit reports more findings than June despite the small code
delta.

Method: 8 parallel read-only audit lanes (telemetry ingest; flow→reroute trigger integrity; reroute
core & concurrency; SSH actuator & templates; auth/RBAC/secrets; frontend; alerts/scheduler/deploy/
deps; June-delta + docs-drift), plus a build-health pass (`cargo test`/`clippy`, `tsc`). **Every
finding graded ≥P2 was then hand-verified against source** — this matters: two lanes proposed P0s that
verification demoted to P1 (see §3), exactly as the June cycle's hand-verification killed 4 false
criticals. This audit is read-only; the confirmed safe fixes are applied separately on branch
`audit-2026-07-fixes`.

## 2. Headline: the core is still sound; the risk has moved to the flow subsystem

**On the shipped default configuration (`observe` mode, flow collector off) there is no reachable P0.**
Every central guarantee the June audit verified still holds, and the two June P1 fixes are real:

- **Observe = GATE 0** in the single shared execution path
  ([executor.rs:115-128](../backend-rust/src/reroute/executor.rs#L115-L128)), read fresh from the DB
  every call; manual, automatic, **and** the new flow-triggered path all funnel through `execute_with`
  and cannot execute in observe (independently verified on the flow call site).
- **Crash recovery (`b86269a`) is correct and regression-free**: `recover_on_startup` checks every
  write, counts failures, and `bail!`s — and because `main.rs:245` propagates with `?`, startup aborts
  before the API/scheduler/dispatcher ever start. No window exists where unrecovered state is served.
- **RBAC per route is clean**: every state-changing route is gated by a `RequirePermission<_>`
  extractor (or the strictest inline admin check on `PUT /api/settings`); **zero mutations are
  reachable by `viewer` or `auditor`**.
- **The SSH actuator is trustworthy**: host keys are TOFU-pinned in the DB and fail closed loudly on
  mismatch; there is no command-injection path (typed re-serialization + `is_name` charclass +
  fail-closed `command_allowed` closed-match); the 4-place command sync (templates/allowlist/RRT-view/
  probe) is intact incl. IPv6; the `shutdown` context guard holds; verification runs in a separate
  read-only session parsing real router output.
- **Crypto is correct**: AES-256-GCM with a random per-seal nonce, tamper-rejected; CSPRNG-generated
  secrets; `.env` written `0600`. Recovery-code consumption is race-safe (`SELECT … FOR UPDATE`).

**The new verdict line — the flow → reroute path — is where the audit found real problems.** Flow
telemetry authenticates the exporter by **UDP source IP alone**, and the `sampling_confidence` gate
that doctrine relies on to "block automatic actions on low confidence" certifies sampling *arithmetic*,
not *source identity*. So once an operator enables flow-driven automatic mitigation (four off-by-default
switches), a spoofing-capable attacker can fabricate a rule firing and steer which prefix is
black-holed (P0-1). The flow collector is also the one network-facing untrusted-input surface, and it
carries three memory-safety P1s (P1-8..P1-10). **None of this is reachable on the shipped default**,
because the flow collector is off — but it must be fixed before the flow subsystem is trusted.

Separately, the **alert-delivery guarantee** doctrine leans on ("`reroute_uncertain`/`reroute_failed`/
security events always reach an admin, never lost") is broken at three independent layers (P1-2..P1-4),
and June's P1-1 fix turns out to be **half-done** — the identical error-swallowing pattern is still
live in the runtime `finalize()` path (P1-2).

## 4. Verified findings

### P0

**P0-1 · Flow telemetry has no source authentication; forged UDP can trigger and steer automatic
reroutes (feature-gated).**
[collector.rs:312](../backend-rust/src/telemetry/flow/collector.rs#L312) authenticates an exporter by
source IP only; [mod.rs:174-193](../backend-rust/src/telemetry/flow/mod.rs#L174-L193) makes the
`reported` sampling tier **unconditionally** high-confidence (and `default` high-confidence at the
shipped `default_sampling_rate=1`); [engine.rs:604](../backend-rust/src/detection/engine.rs#L604)
derives `low_confidence` from that stamp, so forged high-confidence data is **not** blocked by
`should_auto_execute` ([engine.rs:613-619](../backend-rust/src/detection/engine.rs#L613-L619)). NetFlow
v9 and sFlow v5 have no cryptographic authentication and UDP source IPs are trivially spoofable, so an
attacker who can land a datagram with an enrolled device's source IP can fabricate any flow rule's
firing condition at "high confidence". Via `flow_target.rs` auto-target selection, the attacker also
**steers which prefix is black-holed** — bounded to the device's *own* announced prefixes (the
`cidr_contains_host` containment check is sound), i.e. they choose the collateral victim within the
protected estate.
*Precondition (why P0 is not reachable on the default):* requires all four off-by-default switches —
`[flow].enabled`, `operating_mode=enforce`, `automatic_actions_enabled`, and a rule's
`automatic_reroute_enabled` — **plus** spoofing reach to the collector (no BCP38/uRPF on path, or an
on-path/shared segment). GATE 0 respect on the flow path was verified: in observe, nothing executes.
*The compensating control exists but is inert:* the SNMP cross-calibration ratio is computed
([collector.rs:760-822](../backend-rust/src/telemetry/flow/collector.rs#L760-L822)) but only stored for
display — it never forces `sampling_confidence` low, and the "sampling rate likely wrong" flag that
`flow-telemetry.md` documents does not exist in code.
*Fix (report-only — needs a design decision, not a mechanical patch):* wire the existing
`snmp_xcal_ratio` into `sampling_confidence` (force low when out of tolerance); require SNMP
corroboration on the same `(device, if_index)` before flow-driven auto-execution; require N consecutive
corroborating cycles before a new exporter's `reported` rate is trusted as high; and document uRPF/BCP38
as a **hard** requirement for enabling flow-auto. **Until then: do not enable flow-driven automatic
reroutes.** The would-run/observe preview path is safe to keep using.

### P1

The 11 P1s cluster into five themes. Preconditions are stated because most are **not** reachable on the
shipped default.

**Alert-delivery guarantees broken at three layers** (all reachable; 7-3 bites even in observe):

- **P1-1 · Runtime `finalize()` swallows every persistence write — June P1-1 is only half-fixed.**
  [executor.rs:413,427,444,453](../backend-rust/src/reroute/executor.rs#L413-L453) each use
  `let _ = …` with no result check, no `error!`, no counter — the same anti-pattern `b86269a` fixed in
  `recover_on_startup` but **left live in the always-executed runtime path**. If the `uncertain`
  device-lock INSERT (line 427) fails on a transient DB error, the caller still reports "device locked"
  while the `locks` table has no row, and the very next reroute on that device passes the device-lock
  gate. The `reroute_uncertain` alert and audit row may silently fail too. *Actor:* none — a DB blip
  under incident load. *Fix (safe):* port the checked-write pattern from `state_machine.rs` into
  `finalize()`.
- **P1-2 · `reroute_failed` is severity `"warning"`, defeating the documented admin fan-out.**
  [executor.rs:440](../backend-rust/src/reroute/executor.rs#L440) maps `failed → "warning"`, but the
  dispatcher force-adds the admin tier only for `"critical"`
  ([dispatcher.rs:213](../backend-rust/src/alerts/dispatcher.rs#L213)); no default subscription is
  seeded, so on a fresh install a failed reroute reaches **no one** — contradicting `email-alerts.md`
  ("`failed` … always fan out to the admin tier"). *Fix (safe):* `failed → "critical"`.
- **P1-3 · The dispatcher never retries a delivery once any attempt is recorded.**
  [dispatcher.rs:79-87](../backend-rust/src/alerts/dispatcher.rs#L79-L87) selects pending work per
  *alert* (`WHERE NOT EXISTS … alert_deliveries`), so the first transient failure (SMTP greylisting is
  the common case) writes a `failed` row and the alert is excluded forever — including observe-mode
  security alerts (`account_locked`, `2fa_recovery_used`) and `reroute_uncertain`. `email-alerts.md`'s
  "never loses an alert" holds only for the zero-attempts case. *Fix:* select per `(alert, recipient,
  channel)`, retry `failed` rows with backoff to a cap, then raise a `delivery_permanently_failed`
  meta-alert.

**Reroute execution (enforce-mode only):**

- **P1-4 · Global rate-limit (circuit breaker) has a cross-device TOCTOU.**
  `recent_count` is read in `gather()` before any lock
  ([guard.rs:233-237](../backend-rust/src/reroute/guard.rs#L233-L237)); the reservation lock is
  per-device ([guard.rs:263-284](../backend-rust/src/reroute/guard.rs#L263-L284)), so N devices firing
  automatic reroutes together each read the same stale count and all insert, silently exceeding
  `global_action_rate_limit_count` (default 3/600s) — exactly the multi-device event the breaker exists
  to bound. *Fix (safe):* take a single global advisory lock around the rate re-check for automatic
  triggers and re-check the count inside it (mirrors the pattern `reserve_slot` already uses).

**Auth / access (reachable on default):**

- **P1-5 · 2FA-enrollment race — the TOTP secret is handed to whoever supplies a correct password for
  a not-yet-confirmed account.** [auth/mod.rs:189-228](../backend-rust/src/auth/mod.rs#L189-L228): while
  `two_factor_confirmed_at IS NULL`, every login regenerates and returns `totp_enrollment.secret` in the
  response body. For the bootstrap superadmin (2FA deferred to first login), whoever holds the install/
  temp password can self-enroll TOTP, obtain a superadmin session, and lock out the legitimate admin —
  P0-adjacent for that window. *Fix (partial-safe):* stop regenerating/returning the secret on every
  unconfirmed login; alert admins on enrollment completion. Full fix (out-of-band enrollment token) is
  a design change.
- **P1-6 · No re-authentication for the `observe → enforce` mode flip** (June P1-4, still open).
  [settings.rs:132-136](../backend-rust/src/api/settings.rs#L132-L136) gates the single switch that arms
  the whole system on `is_admin()` only — a stolen admin session flips it. `sessions.reauth_at` was
  dropped, so a fix needs either an inline password+TOTP re-check or a new migration. *Report-only*
  (doctrine deliberately removed re-auth once; reintroduction is an owner decision).

**Operator-facing (frontend; enforce-mode only):**

- **P1-7 · Manual-trigger paths don't force a command preview before execution, and one path's UI text
  falsely claims they do.** [ManualReroute.tsx:244](../frontend/src/pages/ManualReroute.tsx#L244)'s
  Execute is independent of the preview action, yet the card states "The exact commands are shown before
  you run anything"; [apply-mitigation-dialog.tsx:151](../frontend/src/components/apply-mitigation-dialog.tsx#L151)
  posts the real apply with no dry-run preview path. Violates doctrine §5.3 ("display exactly which
  reroute will be performed … before any manual trigger"). *Fix (safe):* gate Execute on a shown preview
  / fix the false text; add a dry-run preview to the apply dialog.

**Flow collector memory-safety (precondition: flow collector enabled — off by default):**

- **P1-8 · Unchecked `u64` counter arithmetic on attacker data, two sites.**
  [v9.rs:401-402](../backend-rust/src/telemetry/flow/v9.rs#L401-L402) (`in+out` bytes/pkts) and
  [collector.rs:70-76](../backend-rust/src/telemetry/flow/collector.rs#L70-L76) (`Counts::add`). Debug
  builds panic (violates "never panic"); release builds wrap, letting the attacker pick the resulting
  metric — which **amplifies P0-1** (precise forgery). *Fix (safe):* `saturating_add` at both sites.
- **P1-9 · NetFlow v9 template cache is unbounded and keyed by wire-controlled `source_id` — bypasses
  the `8e74ed5` exporter cap.** [v9.rs:78-99](../backend-rust/src/telemetry/flow/v9.rs#L78-L99): a single
  exporter (works even under the default allowlist, via a spoofed enrolled source IP) grows its own cache
  without bound by varying `source_id`/`template_id` → multi-GB → whole-process OOM abort (takes down
  SNMP, the API, auth — everything). *Fix (safe):* cap the per-exporter cache with LRU, like
  `MAX_EXPORTERS`.
- **P1-10 · Per-bucket talker accumulation is unbounded until flush-time top-K (June P1-3's unfixed
  half).** [collector.rs:97-151](../backend-rust/src/telemetry/flow/collector.rs#L97-L151): confirmed via
  `git show 8e74ed5` that `Accum::fold`/truncation are untouched. A real (or spoofed-reflection)
  volumetric flood via an *enrolled* router — the exact attack the tool exists to characterize — grows
  millions of talker keys → OOM, with no protocol abuse needed. *Fix (safe):* bounded top-K accumulator
  (size-capped heap) folding overflow into the iface/port totals.

**Deployment:**

- **P1-11 · The canonical nginx example forwards the client-supplied `CF-Connecting-IP` and ships its
  protections commented out.** [deploy/nginx/rerouter.conf:37](../deploy/nginx/rerouter.conf#L37) uses
  `$http_cf_connecting_ip` (the raw incoming header), with `set_real_ip_from` and the Cloudflare-only
  `allow/deny` both commented out. An attacker reaching the origin directly forges the client IP →
  defeats per-IP login lockout and forges `audit_logs.ip_address` (compounds P2-e). *Note:* the
  **actually-deployed** dev vhost (`deploy/nginx/emdd.vivanet.ro.conf`) is non-Cloudflare and correctly
  uses `$remote_addr` — this finding is about the documented production template. *Fix (safe):* use
  `$remote_addr`, populate `set_real_ip_from` with Cloudflare ranges, and enforce the Cloudflare-only
  gate.

- **Docs-drift (all safe doc fixes)** — see the ledger in §7.
- **Audit-completeness:** no `audit_logs` row on low-confidence auto-suppression (two sites,
  [engine.rs:689-696,869-884](../backend-rust/src/detection/engine.rs#L689)); `acknowledge_uncertain`

  ([config.rs:119-126](../backend-rust/src/config.rs#L119-L126)); v9 template cache never evicts on
  legitimate churn; `reserve_and_persist` advisory lock has no RAII/panic-safe release (no live trigger);

  insert→pending window (fails toward over-blocking).
- **Hardening:** AES-GCM seals carry no AAD (not app-reachable); sessions have absolute TTL only, no
  idle timeout; `settings.rs` uses an inline `is_admin()` instead of the extractor pattern; dead RBAC
  permissions (`edit_credentials`/`edit_provider`/`edit_asset` gate nothing); systemd unit missing
  `CapabilityBoundingSet`/`RestrictAddressFamilies`/`MemoryDenyWriteExecute` etc.; `cargo-audit` could
  not be run here (deps look current; transitive `rsa 0.10.0-rc.18` pre-release noted, not in the
  vulnerable direction).
- **Config validation follow-throughs (June P3):** enforce `flow.bucket_seconds ≥ 1` in `validate`;
  parse `SocketAddr` for the bind guard; centralize subscription identifiers.

## 6. Doctrine observations (design, not bugs)

- **The doctrine's confidence gate is mis-scoped for the new threat.** Doctrine repeatedly states "low
  parser confidence blocks automatic actions" as the safety property that makes flow-driven auto-action
  acceptable. That gate reasons about *sampling arithmetic*, never *source authenticity* — the actual
  threat once flow feeds reroutes (P0-1). The doctrine text should be updated to state that flow-driven
  automatic execution additionally requires source-corroboration, not just confidence.
- **`CLAUDE.md` promises a server-side "confirmation (for disruptive levels)" gate that was deliberately
  removed** (doctrine §9 + `20260613001000_drop_safety_level.sql`); only frontend confirm dialogs
  remain. This is the first file every agent reads — it should match doctrine (see §7).
- **`executed ≠ succeeded`** (carried from June): the API returns `executed: true` with
  `state: uncertain`; the SPA reads `state` correctly, but the contract is worth a one-line doctrine
  note.

## 9. Verdict

- **Is observe-mode still the shipped, enforced, un-weakened default?** **Yes.** GATE 0 is intact on
  every path including the new flow trigger; the default config is `observe` with the flow collector and
  both automatic switches off.
- **Can an unauthenticated/attacker path cause, suppress, or steer a reroute in enforce mode?** **Only
  if flow-driven automatic mitigation is enabled** (P0-1) — then yes, via source-spoofed flow telemetry.
  With the flow collector off (default), no. Manual and SNMP-driven paths have no such source-spoofing
  hole.
- **Did the 3 delta commits do their job?** `b86269a` (recovery) and `8e74ed5` (exporter cap) are
  correct and regression-free — but each fixed only **half** its problem (`finalize()` still swallows;
  talker accumulation still unbounded). `b46952d` (sFlow) is memory-safe in its own decoder, but it
  completed the wiring that turned flow into a live, spoofable reroute trigger.
- **Net vs June:** the safety-critical **core** is as sound as June found it, and the two June P1 fixes
  are real. The new risk is entirely in **newly-live / newly-audited surfaces** — the flow subsystem
  (1 P0 + 4 P1, all off by default) and the alert-delivery pipeline (3 P1, one reachable in observe).
- **Single most important thing to fix next:** wire source-corroboration into the flow confidence gate
  before anyone enables flow-driven automatic reroutes (P0-1); in parallel, close the alert-delivery
  gaps (P1-1..P1-3), since a silently-lost `uncertain`/`failed` alert is the failure mode doctrine most
  fears.
- **Safe to run in `enforce`?** With the flow collector off and manual/SNMP-driven reroutes only:
  **yes, with the P1-1/P1-2 alert-delivery fixes applied** (so an uncertain/failed action can't fail
  silently). **Do not enable the flow collector's automatic path until P0-1 and P1-8..P1-10 are
  addressed.**
